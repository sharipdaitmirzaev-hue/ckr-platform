# Стратегия резервного копирования ЦКР

Этап 26. Документация для production-эксплуатации.

---

## 1. База данных (Postgres / Supabase)

### Что хранить

- Все таблицы приложения (profiles, projects, deals, documents metadata, notifications, system_logs, …)
- Auth schema (управляется Supabase)

### Рекомендуемый режим

| Слой | Частота | Хранение |
|---|---|---|
| Автобэкапы Supabase (Pro+) | ежедневно / PITR | по тарифу Supabase |
| Логический dump (`pg_dump`) | ежедневно + перед релизом | отдельное хранилище (S3/GCS), 30+ дней |
| Снимок перед миграцией | каждый релиз | минимум 7 дней |

### Восстановление БД

1. Остановить запись (maintenance) при необходимости.  
2. Восстановить из PITR или `pg_restore` / SQL dump в staging → проверка.  
3. Переключить production или восстановить in-place по runbook.  
4. Проверить Auth users и RLS.  
5. Запись в `system_logs`: level=warning, source=`ops.restore`.

---

## 2. Storage (файлы документов)

- Бакет: `documents` (пути `{userId}/{relatedType}/{relatedId}/…`)
- Метаданные файлов — в таблице `documents` (бэкап БД)
- Бинарники: включить версионирование/репликацию бакета или периодический sync в холодное хранилище

### Восстановление Storage

1. Восстановить объекты бакета из snapshot/sync.  
2. Сверить `documents.file_url` с реальными путями.  
3. Удалить «осиротевшие» объекты отдельным job (не в рамках авто-restore).

---

## 3. Секреты и конфиг

- Секреты **не** хранить в git.
- Бэкап списка имён переменных — `.env.example`.
- Значения — в менеджере секретов хостинга / vault; экспорт зашифрованным архивом для DR.

---

## 4. Что не бэкапить как primary

- `node_modules`, `.next` — восстанавливаются из git + `npm ci` + build  
- Demo seed данные — пересоздаются скриптом (не для production)

---

## 5. Проверка целостности

Раз в квартал (или после инцидента):

1. Restore dump в изолированный проект.  
2. `npm run build` против staging env.  
3. Smoke: login, проект, документ, заявка.  
4. Зафиксировать результат в ops runbook.
