## Использованные функции ЦКР

| Контур | Что применялось |
|---|---|
| Организация / партнёр | `/partner`, профиль ООО ТИНДА, members |
| Проект | «Развитие оптовой платформы ТИНДА», стадии, публикация |
| Лия | аудит, стратегия, анализ решений, прогресс, outcome, pilot insight |

| Сделки | пилотная сделка + активность |
| Репутация | профиль организации |
| Pilot ops | `/admin/pilot`, чеклист участника, метрики воронки |
| Outcomes | результаты и финпоказатели, `/admin/results` |

Seed: `npm run seed:tinda` (участник + чеклист с этапа 36).

## Проблемы

1. **CRM-сегменты** задаются через notes — оператору сложно фильтровать клиентов/поставщиков.  
2. **Воронка заявок** у ТИНДА в seed слабее остальных шагов (чеклист: «отправил заявку» — pending).  
3. **Оператор vs admin RLS** — часть CRM-операций требует staff/admin-контекста; путаница ролей.  
4. **Обновление KPI** зависит от дисциплины команды; без ритма прогресс «замирает».  
5. **Feedback** без продвижения в issues/improvements не превращается в изменения продукта.

## Выводы

1. Контур ЦКР **достаточен** для сопровождения реальной организации без новых бизнес-модулей.  
2. Главный риск пилота — не отсутствие функций, а **разрыв между наблюдением и релизом улучшений**.  
3. ТИНДА подтверждает ценность связки: проект → Лия → workspace/KPI → CRM → сделка.  
4. Следующий фокус: закрыть UX/операционные дыры текущего контура и довести 2–3 улучшения до `released`.  
5. Критерий успеха цикла: feedback и issues ТИНДА отражаются в `product_improvements`, а не только в документах.
